### Resultado visible

- PDF, listado, detalle, dashboard e informes omiten las leyendas técnicas de
  cobertura y procedencia, incluidas «Sin snapshot histórico», «Datos de ficha
  actual» y «Datos originales incompletos».
- La evidencia inválida conserva el bloqueo de PDF/QR. La interfaz informa:
  «El PDF no está disponible; consultá al responsable de la instalación».
- Las consultas siguen disponibles; los antecedentes sin evidencia conservan
  la disponibilidad anterior. Los campos faltantes mantienen su representación
  existente, sin completar ni inventar datos.

No se incorporan recuperación moderna PF-04/PF-02, vencimientos desde Excel,
rediseño de emisión masiva, nuevas dependencias ni otras funciones del roadmap.
Los trabajos de planificación ajenos al rango quedan excluidos y conservados.

## Invariantes y checklist aplicable

La revisión del checklist fiscal se limita a los consumidores afectados por
presentación: PDF/QR, comprobantes, dashboard, ventas/IVA y descarga/preview.
No cambia emisión individual, lotes, worker, reintentos ni reconciliación.

- Metadatos de cobertura/origen, evidencia, hashes y vínculos conservados.
- Emisor y punto originales, receptor, importes, moneda, fechas, CAE y estado
  permanecen intactos; no hay recálculo ni reconstrucción de antecedentes.
- El verificador histórico mantiene identidad, pertenencia y coherencia. Ante
  evidencia inválida se conserva HTTP 409 antes de generar PDF o QR.
- Fecha fiscal explícita, confirmación irreversible, idempotencia, reservas,
  estados inciertos y aislamiento entre emisores no cambian.
- Las pruebas usan datos sintéticos y dobles; no solicitan CAE ni consultan ARCA
  real. Los PDF, bases, capturas y logs quedan en evidencia privada ignorada.

El cambio original y esta preparación son Nivel 1 porque sólo retiran textos
de presentación y alinean versión/documentación. El lector, schema histórico,
servicios fiscales, permisos y estado durable no cambian. Se conserva la matriz
completa de CI por incluir runtime; no se exige otra autoreview para una unidad
que no modifica lógica sensible ni amplía el diseño aceptado.

## Actualización y compatibilidad

Desde `v0.3.9` no hay nuevas revisiones Alembic, tablas, columnas, constraints ni
transformaciones de datos. El head continúa en `c3d4e5f6a7b8`.
`alembic upgrade head` debe ser una operación sin cambios sobre una instalación
que ya esté en esa revisión; no corresponde un downgrade de esquema.

No hay cambios de dependencias Python/npm, Dockerfiles, Compose, variables,
puertos o topología. El lockfile frontend cambia únicamente la versión del
paquete raíz. Se conservan Python 3.11, Node 24.15.0, npm 11.12.1, proceso
Uvicorn único, worker y pools separados API `4` y worker `1`, sin overflow.
La construcción frontend mantiene `VITE_API_URL` vacío cuando el servicio se
publica con las rutas `/api` existentes.

Para actualizar se reconstruyen los artefactos desde el SHA aprobado y se
verifica el arranque con el esquema existente. No se repite un traslado de base,
no se importan paquetes operativos ni se cambian certificados.

### Ensayo de actualización, respaldo y retorno

1. Se extrajo el backend del SHA público de `v0.3.9`, usando las mismas
   dependencias del corte, y se inició sobre PostgreSQL 16 sintético en
   `c3d4e5f6a7b8`. Se sembraron cuatro comprobantes mediante los dobles fiscales
   existentes: evidencia completa, incompleta, ausente y no verificable.
2. Login, listado, detalle, ventas/IVA, PDF y preview funcionaron según cada
   cobertura. Las solicitudes con otro emisor fueron rechazadas con HTTP 403;
   la evidencia inválida conservó HTTP 409 para PDF/preview.
3. Con API/worker detenidos, se guardó un respaldo custom en esta PC. La candidata
   ejecutó `alembic upgrade head` sin cambios; el arranque y las consultas
   conservaron el contenido y las secuencias de las 30 tablas de datos y la
   revisión Alembic. La API informó `0.3.10` y los pools permanecieron separados.
4. Se agregó un quinto comprobante con evidencia sintética después del respaldo.
   El retorno al código `v0.3.9`, con su arranque normal y el mismo esquema,
   conservó todas las filas, secuencias y esa escritura posterior. Sus PDF
   volvieron a mostrar las leyendas anteriores; los bloqueos siguieron vigentes.
5. El respaldo almacenado en esta PC se restauró en otra base descartable.
   Contenido y secuencias coincidieron con el punto respaldado; la fuente siguió
   conservando los cinco comprobantes y su evidencia posterior.
6. Se volvió a iniciar la candidata y se repitieron las lecturas. Las cuatro
   coberturas y la separación de pools permanecieron correctas, sin cambios
   de datos ni solicitudes fiscales reales.

La ejecución usó procesos nativos de Python sobre loopback y un único contenedor
PostgreSQL con almacenamiento temporal en memoria. El proyecto de preview
existente no se actualizó para este ensayo. Los guiones privados se ajustaron
para preparar las fixtures sin retirar el guard ORM, respetar el HTTP 403
vigente y transferir el respaldo como bytes en Windows; no fue necesario
corregir código del producto ni relajar pruebas.
Al terminar se retiró el contenedor descartable, sin volúmenes persistentes
creados, y se comprobó que no quedaban servidores temporales de QA. Los dos
servicios del preview existente conservaron su ejecución y salud.

Las capturas E2E muestran la versión `0.3.10`, ausencia de leyendas técnicas y
PDF disponible/bloqueado según corresponda. Los tres PDF sintéticos conservan
identidad original o procedencia actual según el contrato, importes, fechas y
CAE; el dato original ausente sigue sin completarse. Se contrastó el texto
completo con el origen, retirando únicamente las leyendas, y se comparó el QR
embebido sin visitar su URL. El payload y sus bloqueos están cubiertos también
por las pruebas del servicio.

La evidencia concreta, bases, respaldo, scripts, PDF, imágenes y logs permanecen
privados e ignorados. No se versionan archivos operativos ni datos fiscales reales.

## Recuperación y escrituras posteriores

El retorno de aplicación a `v0.3.9` conserva el mismo esquema y los datos,
incluida la evidencia capturada después de actualizar. No requiere ni autoriza
restaurar un respaldo o ejecutar un downgrade. Su efecto visible es volver a
mostrar las leyendas técnicas; conserva las protecciones fiscales anteriores.

El ensayo aislado debe verificar conservación de filas, secuencias y evidencia
entre origen, candidata y retorno, además de restaurar un respaldo sintético en
otra base sin reemplazar la fuente con sus escrituras posteriores.

Un despliegue real necesita respaldo recuperable fresco y copia externa
verificada según el procedimiento privado. La prueba sintética no acredita un
respaldo productivo actual. Un restore real exige una decisión distinta y
preservar operaciones y autorizaciones posteriores.
