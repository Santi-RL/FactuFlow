## Decisión y alcance

Parche PF-03B sobre `v0.3.2`, tag inmutable cuyo commit es
`9c0310d397001a331dc40353815ef9b2359d80de`. Incluye también la reorganización
documental aceptada después de ese tag. El alcance quedó integrado mediante el
PR [`#45`](https://github.com/Santi-RL/FactuFlow/pull/45). El tag anotado
`v0.3.3` y la [GitHub Release](https://github.com/Santi-RL/FactuFlow/releases/tag/v0.3.3),
marcada como `Latest`, apuntan al commit exacto
`3d12c43fc2406b83ab8390e76f5cb1804e5827a4`. El despliegue productivo está
expresamente excluido de este corte.

- Contrato cerrado de ítems y DTO explícito de escritura en la UI.
- Descuentos de 0 a 100, cantidad positiva, precio no negativo y aritmética
  finita; entradas inválidas nunca se sustituyen por cero.
- Formatos oficiales y personalizados, constantes, defaults, perfiles,
  resúmenes de lotes y snapshots revalidados en sus consumidores fiscales.
- Confirmaciones invalidadas al editar; la operación incierta conserva su
  solicitud y clave congeladas hasta reconciliar.

No introduce migraciones, dependencias, cambios de Docker o configuración,
nuevas alícuotas, topes comerciales ni modificaciones a fechas, numeración o
políticas de autorización. PF-19D queda como próximo desarrollo independiente.

## Compatibilidad y aceptación

El diseño y matriz fiscales viven en
[`PF-03B`](../../agents/pf-03b-items-importes-design.md). La serialización del
caso canónico se contrastó con el schema publicado en `v0.3.2`: contenido y hash
idénticos. No corresponde reescribir snapshots válidos ni sanear entradas
desconocidas para forzar su aceptación.

La API rechaza `subtotal`, IDs de respuesta y cualquier propiedad extra de un
ítem. Integraciones ajenas a la UI deben enviar únicamente los campos
documentados en la [guía API](../../api/README.md).

Las pruebas de cierre incluyeron backend completo con PostgreSQL, cobertura
frontend, build, lint/tipos/formato, scripts, E2E, smoke de runtime y auditoría
de dependencias. La revisión final usó `autoreview` con `gpt-5.6-sol medium`.
La evidencia remota se registra de manera independiente del tag.

La QA de navegador usa API simulada: vacío bloqueado, corrección recuperable,
campos exactos, fecha explícita, confirmación irreversible y replay incierto.
Las capturas sintéticas permanecen fuera del repositorio. No se solicita CAE
real ni se evalúan reglas contables nuevas.

Evidencia local completada:

- Suite backend ejecutada con PostgreSQL desechable: 1189 casos, un skip de
  soporte dependiente de plataforma. El fixture de resumen se ajustó a un
  snapshot canónico; la prueba de capacidad mostró interferencia de un worker
  previo en su contador. Ambos casos aprobaron al repetirlos, sin cambiar
  lógica de pools ni relajar aserciones. La cobertura acumulada es 70,31 %
  frente al umbral 69 %. La CI debe confirmar la suite conjunta en Linux.
- 178 pruebas frontend y 34 escenarios E2E aprobados.
- Cobertura frontend: statements 56,36 %, ramas 50,70 %, funciones 43,50 % y
  líneas 57,54 %; supera los cuatro umbrales vigentes.
- Build, Ruff, Black y tipos aprobados; ESLint sin errores, con advertencias
  previas de estilo que no se corrigen fuera de este alcance.
- 27 pruebas de scripts, 5 de seeds y control documental aprobados.
- Runtime Smoke local aprobado: Alembic, salud de API/base y frontend compilado
  sobre PostgreSQL desechable, con worker y capacidad fiscal deshabilitados.
- `npm audit --audit-level=high` y `pip-audit -r requirements.txt` sin
  vulnerabilidades conocidas al verificar el candidato.
- `autoreview` final con Codex `gpt-5.6-sol medium` completado sin hallazgos
  accionables en su umbral configurado P0; sin cambio de modelo ni fallback.
  La revisión manual de consumidores cubrió también compatibilidad, estados
  inciertos y contratos. No se atribuye a la revisión automática cobertura de
  prioridades inferiores a su umbral.

## Recuperación y límite productivo

El rango no cambia Alembic; el rollback es de aplicación al SHA anterior
verificado, sin downgrade ni restauración automática de datos. Una operación
incierta debe reconciliarse antes de cualquier reemisión, también tras rollback.

Para un futuro despliegue, el plano de control debe verificar el SHA y schema
reales, preservar imágenes anteriores para rollback, comprobar un backup
reciente y su restauración, y revisar operaciones fiscales activas. La mera
existencia de archivos de backup no demuestra una restauración válida.

El diagnóstico autorizado fue de sólo lectura. No se modificaron servicios,
bases, imágenes, credenciales, firewall ni configuración del VPS. Una release
publicada no acredita que estas condiciones de despliegue estén satisfechas.
