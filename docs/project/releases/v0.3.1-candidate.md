## Alcance incluido

1. Compatibilidad del importador con el encabezado histórico `PUNTO VENTA` y
   el formato actual `P.VTA.` con columna `ACTIVIDAD`, incluidos documentos
   multipágina con encabezados repetidos.
2. Allowlist exacta y versionada de modalidades Web Services por condición
   fiscal; coincidencias parciales o genéricas permanecen cerradas.
3. Acreditación inicial durable mediante una constancia válida, sin vencimiento
   por el paso del tiempo ni necesidad de volver a cargar el PDF.
4. Comprobación técnica separada con ARCA, recomendada después de 90 días y
   automática antes de emitir cuando está pendiente o desactualizada.
5. Interfaz directa `Importar constancia → seleccionar PDF → resultado`, acción
   manual `Comprobar con ARCA` y estados comprensibles para usuarios no técnicos.
6. Migración Alembic `d1e2f3a4b5c6`, posterior a `c0d1e2f3a4b`, para agregar
   `ultima_comprobacion_arca_en` y retirar la vigencia temporal de la autoridad
   positiva.

## Alcance excluido

- cambios de fecha fiscal, numeración, payload de CAE, idempotencia, reintentos
  o reconciliación;
- nuevas dependencias, cambios de Docker, Compose o configuración productiva;
- solicitudes reales de CAE durante preparación, despliegue o smoke checks;
- tag, GitHub Release o cambios en el VPS durante la preparación local.

## Invariantes fiscales

- Una sincronización técnica nunca acredita un punto que no haya aparecido en
  una constancia válida.
- Un bloqueo, una baja o una ausencia confirmados impiden emitir; una señal
  activa posterior rehabilita el punto conservando la acreditación inicial.
- Si ARCA no responde al preflight automático, la API devuelve `503` antes de
  crear operación, intento, reserva o solicitud de CAE.
- Los replays terminales idempotentes conservan su respuesta durable y una
  carrera posterior al preflight se detecta mediante la revisión fiscal.
- El PDF no se persiste; solo se conservan hash y metadatos probatorios mínimos.

## Migración y rollback

La única migración nueva del rango es `d1e2f3a4b5c6`. El upgrade conserva las
acreditaciones positivas existentes aunque la vigencia antigua haya vencido y
las deja sujetas a comprobación técnica, no a una nueva carga documental.

El downgrade completa las vigencias nulas con la regla histórica de siete días
antes de restaurar las constraints anteriores. Es un rollback fail-closed y no
debe ejecutarse automáticamente: primero se detiene el servicio, se registra el
estado de Alembic y se decide entre rollback de aplicación, downgrade o
restauración.

Para el despliegue autorizado se reutiliza el backup recuperable generado en el
despliegue anterior porque no hubo operaciones productivas posteriores. La
referencia exacta y la comprobación de esa condición pertenecen al plano de
control privado. No se genera un backup nuevo salvo que el preflight contradiga
esas premisas.
