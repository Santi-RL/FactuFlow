# FactuFlow v0.3.4 — autoridad WSFE de puntos de venta

Estado: **PUBLICADO; DESPLIEGUE PENDIENTE**.
Última actualización: 01/09/2026.

## Decisión y alcance

PF-19D se desarrolló sobre `main` en
`2ff7879807ea946b67a23fd644cbf57d35c51f3b` y se integró mediante el PR `#47` en
`38cb4d6dc4faba819292ed8da9b833c68d9b8968`. La release publicada anterior era
`v0.3.3`, cuyo tag apunta a
`3d12c43fc2406b83ab8390e76f5cb1804e5827a4`. Esta release cambia la autoridad,
la preferencia y la presentación de puntos de venta, sin modificar fecha fiscal,
numeración, payload FECAE, idempotencia, reintentos ni reconciliación.

- `FEParamGetPtosVenta` descubre y clasifica puntos por emisor y ambiente; sólo
  un `EmisionTipo` explícito `CAE - …` puede promover elegibilidad.
- `usar_en_factuflow` registra una preferencia compartida por emisor, separada de
  presencia, bloqueo y baja. Los puntos CAE nuevos quedan habilitados por defecto
  y una deshabilitación local no se revierte por sincronizaciones posteriores.
- Número, sistema, presencia, bloqueo y baja son de sólo lectura. Nombre interno,
  domicilio, nombre de fantasía y uso pueden editarse por cualquier usuario
  autorizado del emisor.
- La constancia PDF queda como fuente descriptiva opcional. No consulta WSFE, no
  acredita elegibilidad, no invalida ausentes y no se conserva.
- Individual, perfiles, lotes, worker, reintentos y continuaciones consumen el
  mismo `seleccionable_para_emision`.

El contrato completo y su matriz están en
[`PF-19D`](../../agents/pf-19d-puntos-venta-authority-design.md). La publicación
de una release no determina ni modifica el estado desplegado.

## Migración y recuperación

La migración aditiva `e3f4a5b6c7d8` agrega `usar_en_factuflow`,
`domicilio_fuente`, `nombre_fantasia_fuente` y el tipo de evidencia WSFE. El
backfill habilita puntos Web Services legacy aunque estén bloqueados o dados de
baja temporalmente, conserva fuera los demás y no borra ledger, revisiones ni
fechas de comprobación.

El downgrade es exacto mientras la instalación no haya producido evidencia
`wsfe_param_get_ptos_venta_v1`. Después falla cerrado: un rollback de aplicación
debe conservar el schema compatible o restaurar un backup previo comprobado. El
ensayo exigido cubre upgrade, rollback y reupgrade en SQLite y PostgreSQL
desechable, con conteos y snapshots sintéticos.

Antes de un futuro despliegue, el plano de control debe observar el SHA y schema
reales, comprobar backup y rollback, y descartar operaciones fiscales activas o
inciertas. Este dossier no acredita esas condiciones.

## Aceptación y seguridad fiscal

La sincronización valida el snapshot completo antes de escribir y aplica todos
los cambios bajo locks, compare-and-swap y un único commit. Vacío, duplicado,
tipo ausente, respuesta inconsistente o timeout devuelven `503` y conservan el
estado anterior. Las pruebas utilizan únicamente respuestas sintéticas; ninguna
consulta automatizada usa certificados reales o solicita CAE.

La aceptación debe demostrar:

- CAE compatible, otro sistema, punto nuevo, existente, ausente, bloqueado y
  dado de baja;
- desbloqueo y reaparición con preferencia habilitada o deshabilitada;
- constancia ausente, válida y posterior a datos manuales, con procedencia por
  campo;
- usuarios comunes, administradores, aislamiento multiemisor y separación de
  ambientes;
- abortos preflight con cero operaciones, intentos, reservas y FECAE;
- consumidores individual, perfiles, lotes, worker, reintentos y estados stale;
- confirmación de uso, filtro `Mostrar todos` y preservación de datos
  recuperables;
- migración y rollback en ambos motores.

## Evidencia local

La matriz local completa del 31/08/2026 aprobó:

- backend completo: 1169 pruebas aprobadas, 1 omisión específica de plataforma y
  70,44 % de cobertura, por encima del umbral de 69 %;
- 19 casos enfocados de PF-19D y migraciones SQLite sintéticas;
- 22 pruebas de integración PostgreSQL sobre una instancia desechable, incluido
  upgrade, rollback previo a evidencia, bloqueo fail-closed posterior y reupgrade;
- frontend completo: 180 pruebas aprobadas, con 56,46 % de statements, 50,61 %
  de branches, 43,81 % de functions y 57,65 % de lines;
- 34 recorridos E2E aprobados;
- Runtime Smoke desde PostgreSQL limpio, con migraciones Alembic, health de API y
  base, build del frontend y montaje en preview;
- lint backend y frontend, tipos, build, formato Black, documentación, 27 pruebas
  de scripts y 5 semillas Clawpatch;
- `npm audit --audit-level=high` y `pip-audit`, sin vulnerabilidades conocidas.

Todas las pruebas fiscales usaron datos y respuestas sintéticos; no hubo
solicitudes de CAE ni acceso a producción. El `autoreview` externo exigido por el
checklist fiscal se ejecutó con Codex `gpt-5.6-sol medium` sobre el bundle
completo: seis pasadas, cero hallazgos aceptables o accionables y evaluación
global correcta con confianza 0,99.
