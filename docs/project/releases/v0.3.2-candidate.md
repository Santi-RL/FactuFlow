# FactuFlow v0.3.2 — cierre del candidato

Estado: **CANDIDATO CONGELADO; TAG, PUBLICACIÓN Y DESPLIEGUE PENDIENTES**.

Última actualización: 29/08/2026.

## Decisión de corte

`v0.3.2` es un parche compatible sobre el tag inmutable `v0.3.1`, cuyo commit
es `7afba87b1b56509ffafb7bfefa0dcd23cd2e45a7`. El alcance funcional final quedó
integrado en `main` mediante el merge
`3184187ded0b0941e5240c1b1cc8f88f6d818c93`.

El tag `v0.3.2` debe apuntar al merge exacto del cierre documental posterior a
ese commit y solo puede crearse después de que sus siete checks queden verdes.
Publicar la GitHub Release no despliega ninguna instalación.

## Alcance incluido

1. Preparación de puntos antes de habilitar selectores: cargar, comprobar como
   máximo una vez por emisor cuando corresponde y recargar.
2. Campo aditivo `seleccionable_para_emision`, que exige acreditación RECE,
   estado técnico activo y comprobación ARCA con menos de 90 días.
3. Acción `Comprobar con ARCA` disponible para cualquier usuario autorizado del
   emisor, sin capacidad para acreditar RECE ni modificar otro emisor.
4. Estados normales breves y mensajes accionables únicamente ante una falla,
   un bloqueo o una validación faltante.
5. Conteos de importación mutuamente excluyentes: listos para emitir, no
   disponibles en FactuFlow y requieren revisión.

## Alcance excluido

- cambios de fecha fiscal, numeración, payload de CAE, idempotencia, reintentos
  o reconciliación;
- migraciones, dependencias, cambios de Docker, Compose o configuración
  productiva;
- solicitudes reales de CAE durante preparación, despliegue o smoke checks;
- almacenamiento de constancias, datos reales o evidencia privada.

## Invariantes fiscales

- Una comprobación técnica nunca acredita un punto que no haya aparecido en una
  constancia válida.
- Los puntos pendientes o desactualizados no se seleccionan hasta una respuesta
  positiva; una falla conserva únicamente los puntos todavía frescos.
- La acreditación inicial no vence por tiempo y el umbral técnico continúa en
  90 días.
- El preflight final del servidor permanece antes de crear estado fiscal o
  alcanzar `FECAESolicitar`; una falla de ARCA deja cero operaciones, intentos,
  reservas y solicitudes de CAE nuevas.
- Una respuesta vacía, inconsistente o fallida de ARCA no modifica estados y el
  aislamiento por emisor se mantiene.

## Base, rollback y backup

El rango `v0.3.1..v0.3.2` no contiene migraciones. Alembic debe permanecer en
`d1e2f3a4b5c6` antes y después del despliegue; no corresponde ejecutar upgrade
ni downgrade de base.

El rollback es exclusivamente de aplicación al tag inmutable `v0.3.1`
(`7afba87b1b56509ffafb7bfefa0dcd23cd2e45a7`). Si el preflight confirma ese
origen, la ausencia de cambios de schema y que no hubo operaciones fiscales
posteriores relevantes, puede reutilizarse el backup vigente. Si cualquiera de
esas premisas falla, debe obtenerse un backup nuevo antes de mutar producción.

## Procedimiento de publicación y despliegue

1. Integrar este cierre con los siete checks verdes y verificar `main` limpio.
2. Crear el tag anotado e inmutable `v0.3.2` sobre ese merge exacto.
3. Publicar la GitHub Release como `Latest` con las notas de este dossier y
   `CHANGELOG.md`.
4. Registrar la publicación mediante un cierre documental separado.
5. En `vps-admin`, comprobar que producción parte realmente de `v0.3.1`, que
   Alembic está en `d1e2f3a4b5c6` y que el rango no introduce migraciones,
   dependencias, Docker ni configuración.
6. Desplegar únicamente FactuFlow desde el SHA del tag y verificar que Alembic
   no tenga cambios pendientes.
7. Ejecutar health, worker/pools, login, emisor activo, UI de puntos de venta y
   una comprobación segura `FEParamGetPtosVenta`, sin emitir ni solicitar CAE.
8. Revisar logs, confirmar ausencia de `FECAESolicitar`, salud de servicios
   vecinos y el SHA finalmente observado.

Una discrepancia de SHA, schema, backup, operaciones fiscales o estado
productivo detiene el flujo y requiere una decisión antes de continuar.
